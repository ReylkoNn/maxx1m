# Max1m: состояние безопасности и план

Это не аудит и не подтверждение безопасности уровня Signal. Не используйте
текущую версию для информации, компрометация которой неприемлема.

## Срочно

- Обновить **и клиенты, и сервер**: старый клиент продолжал отправлять
  незашифрованные кадры демонстрации экрана через WebSocket даже если новый
  сервер их не пересылает. В обновлённом клиенте демонстрация экрана полностью
  переведена на изолированный сквозной WebRTC DTLS-SRTP видеоканал
  (`ScreenPeerSession`, `channel="screen"`) на отдельном потоке и отдельном
  `RTCPeerConnection` с подписанным и зашифрованным сигналингом (`SignalCrypto` +
  `call_envelope`), а приём любых незашифрованных WS-событий `screen_frame` /
  `screen_control` заблокирован.
- Использовать доверенный туннель с HTTPS/WSS; не публиковать сервер напрямую по
  HTTP. Туннель защищает соединение до конечной точки TLS, но не является E2EE.
  Десктопный клиент теперь отклоняет незашифрованный `http://` для любых
  не-loopback хостов (разрешены только `https://` и локальные `127.0.0.1` /
  `localhost` / `[::1]` для локального туннеля или разработки; переопределение
  `MAX1M_ALLOW_INSECURE_HTTP=1` предназначено исключительно для изолированных
  лабораторных стендов). При работе сервера за локальным reverse proxy /
  туннелем задайте `TRUSTED_PROXY_IPS` (например, `127.0.0.1,::1`), чтобы
  ограничитель частоты запросов определял IP клиента по `X-Forwarded-For`
  справа налево только от доверенных прокси; не добавляйте в `TRUSTED_PROXY_IPS`
  недоверенные сети. Интерактивная документация `/docs`, `/redoc`,
  `/openapi.json` по умолчанию отключена (`ENABLE_API_DOCS=false`), а ответы HTTP
  снабжаются заголовками `Cache-Control: no-store`,
  `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY` и
  `Referrer-Policy: no-referrer`.
  Новый клиент передаёт WebSocket-токен в заголовке Authorization. Старые клиенты
  всё ещё используют строку запроса, которую сервер пока принимает ради
  совместимости (`ALLOW_LEGACY_WS_QUERY_TOKEN=true`); после обновления всех
  клиентов установите `ALLOW_LEGACY_WS_QUERY_TOKEN=false`, чтобы полностью
  отклонять `?token=` и исключить попадание JWT в URL-журналы прокси.
  В логах Uvicorn добавлена маскировка как `?token=`, так и `Bearer`-токенов, но
  логи туннеля/прокси и другие журналы необходимо настроить отдельно. Не
  записывайте Authorization в логи.
  Новый клиент требует обновлённого сервера и не возвращается к токену в URL.
- Проверить уже отслеживаемые `.env`, базы, загруженные файлы и bytecode на
  секреты и приватные данные; заменить скомпрометированные ключи. `.gitignore`
  не удаляет файлы из индекса или истории Git. Не переписывать историю без
  плана резервирования и согласования.
- Запускать один экземпляр/worker сервера: WebSocket-соединения находятся в
  памяти процесса. Несколько экземпляров потребуют общего маршрутизатора событий.
- HTTP проверяет состояние пользователя, устройства и версии JWT-сессии
  (`Device.session_version`) при каждом запросе; открытый WebSocket
  перепроверяется каждые 5 секунд и закрывается при отзыве устройства, выходе из
  сессии, отключении пользователя или истечении токена. Добавлены `GET /auth/devices`,
  атомарный `POST /auth/devices/{id}/revoke`, серверный отзыв сессии
  `POST /auth/logout` (сброс текущей сессии, всех сессий аккаунта или только
  остальных устройств без безвозвратного отзыва криптографического устройства) и
  смена пароля аккаунта `POST /auth/change-password` с проверкой/хешированием
  Argon2id вне event loop, редакцией секретов в ответах `422`, безусловным
  аннулированием активных сессий остальных устройств и их опциональным полным
  отзывом (под `BEGIN IMMEDIATE`, с немедленным закрытием WebSocket в текущем
  серверном процессе), а также управление паролем, сессиями и устройствами в
  настройках клиента (с локальным пересчётом отпечатка SHA-256 по публичному
  ключу каждого устройства и проверкой неизменности публичного ключа текущего
  устройства). На сервере параметры Argon2id берутся из `ARGON2_*` с прозрачным
  обновлением устаревших хешей при входе, алгоритм JWT ограничен симметричным
  списком `HS256`/`HS384`/`HS512`, а несовпадающие канонические отпечатки
  устройств (`XXXX:XXXX:...:XXXX`) блокируются при регистрации и добавлении
  устройства (строгий режим для всех ключей — `REQUIRE_VERIFIED_DEVICE_KEYS=true`).
  На стороне десктопа при закрытии WebSocket с кодом `1008`
  или отказе рукопожатия `401/403` клиент немедленно проверяет сессию через HTTP
  и при подтверждённом `401/403` автоматически останавливает фоновые циклы и
  звонок, сбрасывает ссылки на токен и ключи из состояния окна (с учётом того,
  что среда выполнения Python не гарантирует криптографического затирания
  неизменяемых строк в куче), очищает отображение чата и возвращает пользователя
  на экран входа с сохранением зашифрованных локальных очередей на диске;
  локальные каталоги профиля/сообщений/очередей/голосового кэша на POSIX создаются
  с правами `0700` (`local_state.json`, `history_catalog.enc`, элементы `voice_cache`
  и журналы защиты от повтора звонков — `0600`), а на сервере каталоги `DATA_DIR` /
  `secure_uploads` и загруженные блобы/файлы БД ограничиваются правами `0700`/`0600`.
  Межпроцессная синхронизация WebSocket при нескольких воркерах пока отсутствует.
- Настроить ограничение размера запросов и количество параллельных запросов на
  туннеле/обратном прокси: multipart-парсер legacy endpoint обрабатывает тело до
  вызова upload. Надёжный upload использует потоковое сырое тело, но для обоих
  endpoint всё равно необходимы лимиты соединений и запросов на прокси.
  Парольные операции выполняются в отдельном пуле: до двух одновременно и до
  восьми ожидающих; при перегрузке сервер возвращает 503. Это не заменяет лимиты
  на уровне прокси. Для WebSocket установлены ограничения размера сигналов; при
  запуске сторонней командой Uvicorn также задайте `--ws-max-size 131072`.
- Для надёжной синхронизации личных сообщений обновить сервер и каждый клиент.
  Новый клиент использует `/messages/sync-safe` и подтверждает обработку через
  `/messages/ack`; старый `/messages/sync` оставлен для совместимости и по-прежнему
  помечает сообщения доставленными до подтверждения. Старый клиент не получает
  новых гарантий. Старый сервер не поддерживает новый протокол: клиент предупредит
  об этом и не будет откатываться к небезопасной синхронизации.
  Для групп на сервере и в клиенте добавлен защищённый протокол групп E2EE v2
  (`/groups/v2/create`, `/groups/v2/{id}/distribute-key`, `/groups/v2/invite`,
  `/groups/v2/send` + `/groups/sync-safe` и `/groups/ack`) с односторонним
  симметричным `HMAC-SHA256` ratchet на каждое сообщение, окном внеочередных
  ключей (`MAX_SKIP=256`), привязкой к эпохе состава (`epoch`), серверной и
  клиентской проверкой канонической подписи Ed25519 и шифрованным локальным
  хранилищем ключей `group_keys.enc`. Клиент подтверждает групповые сообщения
  через `/groups/ack` только после успешной проверки и локальной записи, и не
  использует старый разрушительный `/groups/sync`. Это по-прежнему SenderKey
  v2 (а не стандартизованный IETF MLS с treekem post-compromise healing без смены
  состава).
  Для исходящих личных текстов, команд удаления (`delete_msg`) и метаданных уже
  загруженных вложений добавлена локальная зашифрованная очередь (до 1000 записей)
  и идемпотентный endpoint `/messages/send-reliable`. Один и тот же зашифрованный
  пакет повторяется с тем же UUID после сбоя, поэтому успешная отправка с
  потерянным ответом не создаёт вторую запись. Клиент и сервер необходимо
  обновить одновременно. Старый сервер не поддерживает этот endpoint; клиент не
  пытается небезопасно отправить через старый.
  Локальные данные истории сохраняются внутри зашифрованной записи очереди до
  отправки и восстанавливаются идемпотентно перед сетевым запросом. Это не
  полноценная транзакция двух файлов и не защита от потери локального ключа.
  Для изображений и голосовых сообщений добавлена отдельная сохраняемая очередь:
  зашифрованный файл и метаданные записываются до загрузки, а после выдачи
  доступа получателю неизменяемое сообщение переносится в очередь исходящих.
  Повторы используют постоянные UUID файла и сообщения. Нужны обновлённые клиент
  и сервер: старый сервер не поддерживает `/files/upload-reliable/{id}`, отката
  к старому endpoint нет. До 50 вложений и 128 МиБ шифротекста на очередь;
  повторы после ошибки ограничены интервалом пять минут. Отключённые/сменившие
  ключ контакты блокируют отправку. Автоматические повторы не гарантируют
  доставку при потере локальных ключей или удалении данных сервера.
  После аварийного завершения могут остаться осиротевшие клиентские шифротексты;
  временные серверные `.upload-*` файлы на POSIX защищены `flock` во время приёма
  и безопасно очищаются при рестарте, если процесс-отправитель завершился, а
  зависшие записи `upload_reservations` без `FileRecord` и **без** опубликованного
  блоба на диске очищаются по TTL (`UPLOAD_RESERVATION_TTL_SECONDS`, по умолчанию
  24 часа) при старте и лениво при исчерпании квоты (либо вручную владельцем через
  `DELETE /files/upload-reliable/{id}`). Брони, у которых блоб уже слинкован на
  диск, автоматически не удаляются, чтобы сохранить привязку владельца для повтора.
  Не удаляйте файлы клиентской очереди вручную, не убедившись, что они не
  относятся к ожидающим сообщениям.
  При повторном открытии чата или перезапуске индикатор ожидания (`⏳`) для
  неотправленных сообщений и вложений восстанавливается по зашифрованным
  очередям `outbox`/`attachment_outbox`, а ожидающие загрузки свои изображения и
  голосовые сообщения читаются и аутентифицируются локально без ложного запроса
  к серверу; обычная отметка `✓` разделена от подтверждения прочтения `✓✓`.
  При удалении сообщения в клиенте входящие сообщения собеседника удаляются
  только локально (без ложной отправки неисполнимого `delete_msg`), а удаление
  своего ещё не отправленного сообщения или вложения одновременно отменяет его
  запись в `outbox` / `attachment_outbox` и серверную бронь загрузки, не допуская
  повторного появления в истории или утечки при восстановлении связи; в меню чата
  также доступна явная отмена всей очереди ожидающих вложений, а для read-only
  проверки целостности профиля без раскрытия секретов добавлен CLI
  `max1m_desktop/diagnose_profile.py`.
  На сервере подтверждённые (`is_delivered=true`) личные сообщения старше
  `DELIVERED_MESSAGE_RETENTION_SECONDS` (по умолчанию 7 суток) автоматически
  сворачиваются в легковесные `message_idempotency` tombstone-записи с
  SHA-256-дайджестом конверта (хранятся `IDEMPOTENCY_TOMBSTONE_TTL_SECONDS`, по
  умолчанию 30 суток), что освобождает таблицу `messages` от старых шифротекстов
  при сохранении идемпотентности `/messages/send-reliable`, защиты от `409` и
  работоспособности курсора `after` в `/messages/sync-safe`.
- При неизвестном отправителе, ошибке проверки подписи или сохранения клиент не
  подтверждает сообщение; оно остаётся на сервере и повторяется при синхронизации.
  Это доставка как минимум один раз, а не гарантия бесконечного хранения сервера,
  восстановления потерянных ключей или защиты от недоверенного сервера.

- Небезопасные legacy-маршруты групп (`/groups/create`, `/groups/invite`,
  `/groups/send`, `/groups/sync`) по умолчанию остаются заблокированы (`503`):
  прежняя реализация v1 не обеспечивала привязки контекста, симметричного
  ratchet и контроля эпох. Вместо них в клиенте и на сервере работает протокол
  групп E2EE v2 (`/groups/v2/*` + `/groups/sync-safe` + `/groups/ack`), где
  добавление и выход участника увеличивают `epoch` и запускают ротацию
  `SenderKey` только между проверенными участниками. Старые клиенты v1 получают
  `503` на обновлённом сервере; опция `ALLOW_INSECURE_LEGACY_GROUPS=true`
  предназначена только для осознанной миграции. Выход участника защищает новые
  сообщения следующей эпохи, но не может отобрать сообщения и ключи прошлых эпох,
  которые вышедший участник уже получил до выхода.
- Управление вызовами и сигналы WebRTC в новом клиенте дополнительно подписаны,
  зашифрованы и привязаны к устройствам и случайному ID конкретного вызова.
  Повторное входящее предложение блокируется локально, в том числе после
  перезапуска; события текущего вызова дедуплицируются в памяти. Старые клиенты
  несовместимы: их неподписанные сигналы отвергаются. Нужны корректные часы на
  обоих устройствах (допустимо расхождение не более пяти минут); удаление или
  откат локального хранилища может ослабить защиту от повтора. Сервер по-прежнему
  может задерживать и блокировать звонки. Перед звонком требуется ручная сверка
  отпечатка по независимому каналу; при повторном поиске изменившиеся ключи не
  подменяются. Для новых личных сообщений и вложений также требуется ручное
  подтверждение отпечатка перед постановкой в очередь. Перед каждым повтором
  очередь, включая старые записи, проверяет ключ получателя и собственную подпись,
  а также локально расшифровывает пакет с проверенным ключом. При несовпадении
  запись остаётся в очереди и не отправляется. Входящие сообщения пока не
  блокируются до проверки. Это не независимый аудит и
  не Signal-протокол. TURN настраивается
  через окружение, но реальные соединения пока не испытаны.

## Следующие этапы

1. Добавить интеграционные тесты и измерения памяти, восстановить и закрепить
   зависимости десктопа на целевых ОС, проверить доставку с подтверждениями.
2. Исправить жизненный цикл групп, хранение и распределение ключей, отключить
   небезопасные операции до появления проверенной реализации.
3. Выбрать поддерживаемую реализацию проверенного протокола с ratchet, проверить
   лицензирование и совместимость с Python; разработать миграцию ключей и истории.
   Не объявлять совместимость с Signal без соответствующей реализации и аудита.
4. Проверить аутентификацию WebRTC, добавить настраиваемый TURN и тесты в разных
   сетях; перевести демонстрацию экрана на аутентифицированный E2EE медиаканал.
5. Ввести постраничную историю, ограниченные кэши и потоковую обработку вложений
   на клиенте; измерить потребление памяти и задержки на типовых устройствах.
6. Независимый аудит безопасности, тестирование на отказ и review интерфейса.

## Проверка текущих серверных регрессий

Из `max1m_backend`, в виртуальном окружении Python 3.11:

```
pip install -r requirements-test.txt
python -m pytest -q tests
```

Тесты используют временную базу и не должны работать с пользовательскими данными.

Для отдельных тестов клиента из `max1m_desktop`:

```
pip install -r requirements-test.txt
python -m pytest -q tests
```

Это минимальные зависимости тестов, а не полный список для запуска приложения.
GUI-тест использует Qt в режиме offscreen и требует системных библиотек Qt/OpenGL;
без них он пропускается. Аудио и WebRTC в этих тестах заменены заглушками.

## Проба OpenMLS

Синтетический эксперимент и команды запуска находятся в
[`experiments/openmls-probe`](experiments/openmls-probe/README.md). Базовый обмен
двух участников работает, но имеющаяся экспериментальная WASM-обёртка имеет
блокеры смены состава, обработки повреждённых данных и сохранения состояния.
Это не production-интеграция; группы не включены. Подробности и ограничения —
в README эксперимента и [оценке протоколов](docs/protocol-evaluation.md).

План реализации по одному пункту — в [docs/WORK_ITEMS.md](docs/WORK_ITEMS.md).


## Входящие устройства и границы доверия

Пункт 2 плана: только уникальный локальный device ID с вручную сверенным
отпечатком в области (аккаунт, сервер, своё устройство), валидной подписью и
успешной расшифровкой допускается к обработке. Ошибки идентичности и записи не
ACK-аются, после сверки запускается повторный safe sync. Старые не привязанные
к области отметки требуют новой сверки и исходящая очередь также ждёт её.
Новые устройства добавляются по явному согласию, но не получают доверие от
сервера; смена/удаление сохранённых ключей автоматически не принимается.
Старая история не становится проверенной задним числом. Это не защищает от
скрытия, задержки и криптографических повторов сервером и не заменяет ratchet.
Настоящий Qt GUI end-to-end в этом окружении не проверен.

## Ratchet: ограниченная экспериментальная проверка

В `experiments/ratchet-probe` проверены X3DH и Double Ratchet сторонних Python-
библиотек с синтетическими данными. Обнаружены блокеры интеграции: prekey
расходуется до проверки первого ciphertext; пропуски сверх порога при смене
цепочки могут сделать отложенные сообщения нерасшифровываемыми; применение
рекомендуемого AES/HMAC требует исследования сравнения тегов. Транзакции
состояния, очереди и истории, сервер prekey, защита от отката и миграция пока
не реализованы. Рабочий клиент не использует эксперимент; пункт 3 не завершён.


## Группы и звонки: дополнительное ограниченное укрепление

В default-конфигурации сервера `/groups/sync` теперь возвращает 503 вместо
преждевременного destructive ACK. `/groups/sync-safe` сохраняет сообщения;
небезопасный opt-in оставляет старое поведение. MLS по-прежнему не реализован.
Звонок привязывается к уникальному локальному снимку проверенного устройства;
изменение ключа/области доверия блокирует передачу сигналов и вызывает запрос
завершения сессии. При сбое создания аудиосессии захват закрывается, события
WebRTC передаются в GUI через Qt. Проверки автоматизированы на заглушках, не на
аудиоустройствах/сетях; жизненный цикл быстрых повторных звонков и TURN ещё
не подтверждены. Пункты 4 и 5 плана остаются незавершёнными.


## Пакеты I–IV: максимальное укрепление против перехвата ТСПУ/MITM, изъятия сервера, обыска устройства и блокировок звонков

1. **Пакет I — Защита от MITM / Rogue CA, анализа трафика и изъятия сервера:**
   - **TLS SPKI Pinning (`max1m_desktop/app/tls_pinning.py`)**: жёсткая сверка
     отпечатка `sha256/<base64(SHA256(SubjectPublicKeyInfo))>` сертификата листа
     или промежуточного УЦ для всех HTTPS (`urllib3.connection.HTTPSConnection`)
     и WSS (`websockets.connect`) соединений **до** отправки токенов и полезной
     нагрузки (включая защиту от доверенного корневого Rogue CA на провайдере/ТСПУ).
   - **Криптографическое выравнивание трафика (`pad_traffic_bytes` / `unpad_traffic_bytes`)**:
     все личные и групповые текстовые шифротексты выравниваются CSPRNG-шумом по
     корзинам `512 .. 65536` байт для подавления side-channel анализа длины фраз.
   - **Шифрование названий групп (`"[E2EE]"`) и анти-изъятие сервера**: сервер
     получает только `name="[E2EE]"`, реальное имя распространяется в E2EE
     метаданных `SenderKey`; на сервере включены `PRAGMA secure_delete=ON` и
     `PRAGMA temp_store=MEMORY`, `Device.last_seen` огрубляется до часа
     (`LAST_SEEN_GRANULARITY_SECONDS=3600`), а одиночные блобы файлов
     (`st_nlink == 1`) затираются нулями перед `os.unlink`.

2. **Пакет II — Анти-обыск на устройстве пользователя:**
   - **Локальный сейф `Argon2id` без OS `keyring` (`max1m_desktop/app/local_vault.py`)**:
     опциональный мастер-пароль переносит приватный ключ устройства и локальный
     ключ истории в `vault.enc` (`Argon2id` `64 MiB`, `time_cost=3` + `XSalsa20-Poly1305`),
     физически удаляя копии ключей из системного `keyring` ОС и удерживая ключи
     в `bytearray` в RAM только на время разблокированной сессии.
   - **Автоблокировка (`Ctrl+Shift+L` и таймер простоя)**, **код под принуждением
     (Duress PIN)** (при вводе ложного пароля мгновенно уничтожает боевые ключи,
     истории и кэши с перезаписью и открывает чистый профиль-приманку без
     криминалистических следов наличия второго кода) и **Panic Wipe
     (`Ctrl+Shift+Backspace`)** (`secure_wipe_file` — проход случайными байтами +
     нулями + `fsync`).
   - **Исчезающие сообщения (TTL)** в личных чатах, группах v2 и вложениях с
     физическим затиранием в SQLite (`secure_delete=ON`) и фоновым жнецом каждые 5 с.

3. **Пакет III — Боевой асинхронный X3DH + Signal Double Ratchet для личных чатов:**
   - Боевой роутер `/prekeys` (`ENABLE_PREKEYS=true`: `GET /prekeys/status`,
     `PUT /prekeys/bundle`, `POST /prekeys/{target_device_id}/claim`) с
     обязательной проверкой подписи Ed25519 над `X3DH_CURVE25519_PREFIX || signed_prekey`,
     квотами OPK и автоматическим `3-DH` fallback при исчерпании одноразовых ключей
     (экспериментальный `/experimental/prekeys` сохранён выключенным `503` для
     обратной совместимости тестов).
   - Клиентское ядро `max1m_desktop/app/double_ratchet.py`: X3DH (`4-DH`/`3-DH`),
     Signal Double Ratchet (симметричный `HMAC-SHA256` KDF + асимметричный
     `X25519` DH-шаг на каждом развороте диалога — Forward Secrecy и
     Post-Compromise Security), транзакционное SQLite-хранилище `ratchet_v1.sqlite3`
     (`secure_delete=ON`, шифрование всех ключей сессии локальным ключом сейфа,
     ограниченный кэш пропущенных ключей `MAX_SKIP=256` и двухфазная crash-safe
     таблица `seen_incoming` + `mark_delivery_persisted` с защитой от потери
     сообщений при аварийном отключении питания до записи истории), интегрированное
     в `incoming_identity.py` и `outbox_policy.py` (`attachment_commitment` для
     вложений) с плавным прозрачным переходом со статического `Box`.

4. **Пакет IV — Автономные звонки в РФ без VPN и голосовые комнаты 2–8 человек:**
   - Серверный эндпоинт `GET /calls/ice-config` выдаёт краткоживущие `HMAC-SHA1`
     учётные данные `coturn` (`CALL_TURN_URLS`, включая `turns:<host>:443?transport=tcp`
     поверх TCP/TLS 443 для прохождения ТСПУ и корпоративных файрволов без VPN),
     а в настройках клиента добавлен тумблер **«Скрывать мой IP при звонках
     (Relay-Only через TURN)»** (отключает STUN, переводит `aioice` в
     `TransportPolicy.RELAY` и вырезает не-relay кандидаты из SDP и trickle ICE).
   - В группах реализованы RAM-only голосовые комнаты на `2–8` участников
     (`/calls/groups/{id}/voice/{state,join,leave,signal}` + `group_voice_room.py`)
     со сквозным подписанным и зашифрованным сигналингом SDP/ICE, одиночным
     захватом микрофона с fan-out раздачей, `VoiceActivityGate` (гистерезисный
     Noise Gate / VAD + режим рации Push-to-Talk на клавишу `V` с хвостом `180 мс`),
     20-мс многоканальным микшером `GroupAudioMixer` с индивидуальной громкостью
     каждого собеседника `0% – 200%` и soft-knee `tanh` лимитером без клиппинга,
     живой индикацией говорящего и просмотром демонстрации экрана участника в 1 клик.
