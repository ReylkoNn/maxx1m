# Изолированная проба X3DH + Double Ratchet

**Не использовать в приложении или с реальными ключами.** Это лабораторный тест
на синтетических данных в одном Python-процессе, а не реализация протокола Maxx1m,
не аудит и не Signal-совместимость. Рабочий клиент не импортирует этот каталог.

Изучены поддерживаемые авторами независимые Python-библиотеки:

* `doubleratchet==1.3.0`, MIT, исходники
  [tag v1.3.0](https://github.com/Syndace/python-doubleratchet/tree/30473a1816734540f698703db0574e5f01f41c77),
  SHA-256 колеса `a869c81aa175abd9d7cfcf0069a0fa1261116b2ff2684c1ac95a1b83b875b18d`.
* `x3dh==1.3.0`, MIT, исходники
  [tag v1.3.0](https://github.com/Syndace/python-x3dh/tree/b39a6d3ff81628a18785cc340df010f6c97381e9),
  SHA-256 колеса `92548974e0cd9eccf19315f59014e5796ee4c5440b6fe753a9168fb92dd6c914`.

Совпадение PyPI-артефактов с указанными исходниками и независимый аудит не
установлены. Обе библиотеки разработаны не Signal и не являются libsignal.
Файл зависимостей фиксирует прямые версии для повторения пробы, но **не является
полным lock-файлом**, не требует хеши и не годится для production-сборки.
Проверялась только Linux x86-64 / Python 3.11.

```sh
python -m venv /tmp/maxx1m-ratchet-probe
/tmp/maxx1m-ratchet-probe/bin/pip install -r requirements.txt
/tmp/maxx1m-ratchet-probe/bin/python -m pytest -q --disable-warnings
```

Из этой директории. Тесты подтвердили обмен X3DH и ratchet, двусторонние сообщения,
восстановление из JSON в памяти, нарушение порядка в пределах лимита, повтор,
повреждённый ciphertext, привязку associated data, ограничение пропусков,
ошибочную подпись prekey и соответствие Ed25519 public key из того же seed,
который используется PyNaCl. Это не подтверждает корректность миграции ключей.

## Что выяснилось

1. `x3dh.State.get_shared_secret_passive` удаляет одноразовый prekey и вызывает
   `_publish_bundle` **до** аутентификации первого ratchet ciphertext. Если
   подключить её напрямую, испорченный первый пакет расходует ключ и оригинал
   больше не обрабатывается. Тест демонстрирует это. Второй тест демонстрирует
   отбрасывание изолированной копии состояния, но не решает persist или
   побочные эффекты публикации; настоящий обработчик обязан отложить их до
   атомарной фиксации после успешной аутентификации.
2. При переходе на другую DH-цепочку, если пропущено больше установленного
   порога, библиотека предупреждает и продвигается вперёд без сохранения старых
   ключей; в воспроизводимом тесте задержанные сообщения затем не расшифровать.
   Это риск потери сообщений при offline/reordering, а не только расход памяти.
   Нужны явная политика упорядочения/задержки и отказ без ACK до её проверки.
3. В `doubleratchet` 1.3.0 рекомендуемый `aead_aes_hmac` сравнивает теги Python
   оператором `!=`, а не явно через постоянное по времени сравнение. Воздействие
   не исследовано; это блокер для security review и не оценка всей библиотеки.
4. Ratchet потребляет ключ сообщения. Текущая проверка исходящей очереди из
   пункта 1 расшифровывает собственный шифротекст статическим ключом получателя —
   для ratchet она неприменима. Новая транзакционная очередь должна хранить
   точные байты ciphertext, подтверждённую привязку устройства и состояние
   до/после шифрования атомарно; нельзя заново шифровать при сетевом повторе.
   Получатель должен атомарно фиксировать новое состояние, историю и dedup ID
   до ACK. Тест копирования исходящего состояния не является такой транзакцией.
5. Сервер должен атомарно выдавать каждому инициатору отдельный одноразовый
   prekey, хранить только публичные части, поддерживать offline, идемпотентный
   retry, пополнение и ротацию; нельзя доверять identity key из ответа сервера.
   Нужны защита от downgrade, параллельных начальных сессий, конфликта версий,
   сбоев и отката snapshot, политика отзыва устройств и проверка по независимому
   каналу. Ничего из этого этот тестовый код не реализует.
6. `json` состояния содержит секреты; JSON в тесте не шифруется и не записывается
   на диск. Для приложения необходимо защищённое транзакционное хранилище с
   контролем конкуренции. Нужны тесты сбоя процесса и питания, миграции и защиты
   от rollback. Необратимое удаление ключей на обычных файловых системах не
   гарантируется.

Перед выбором зависимости необходимо проверить актуальную поддержку и CVE,
лицензии, исходники, фиксированные сборки для целевых ОС и организовать
независимый аудит. Для безопасности старые и новые протоколы нельзя незаметно
переключать или считать старые сообщения имеющими forward secrecy.

## Транзакционное хранение — учебный прототип

`transaction_store.py` отдельно от приложения демонстрирует SQLite-транзакцию:
состояние, исходный ciphertext и исходящая история фиксируются вместе; при
приёме — новое состояние, история и сохранённый digest пакета. Для точного
повтора сохранённого пакета проверяется digest внутри аутентифицированной
записи, чтобы подтвердить только уже записанное сообщение, не тратя ratchet-ключ
второй раз. Конфликт ID отвергается. Версия состояния проверяется в транзакции
при параллельных обработчиках; тесты на SQLite показывают, что второй обработчик
с устаревшим состоянием не перезаписывает первый. Тест с настоящими библиотеками
имитирует ошибку перед commit, рестарт объекта и точный повтор ciphertext.

Это исследовательский код, не миграция и не продакшен-хранилище: секретный ключ
просто передаётся в конструктор, нет квот, блокировки внешнего отката базы,
контроля целостности всей истории или комплексных тестов с убийством процесса и
отключением питания. SQLite и файловая система могут сохранять старые страницы,
журналы и резервные копии с зашифрованными прошлыми состояниями: при последующей
компрометации долговременного ключа хранилища это ослабляет forward secrecy.
Защищённое удаление ключей не гарантировано. Метаданные SQLite (в том числе ID
записей, число и размер) не скрыты. Не использовать с настоящими данными.

## Отдельная серверная проба выдачи публичных prekey

В коде сервера добавлен **по умолчанию выключенный** экспериментальный API:
`PUT /experimental/prekeys/bundle` публикует подписанный публичный prekey и до
100 публичных одноразовых ключей своего устройства;
`POST /experimental/prekeys/{device_id}/claim` с UUIDv4 запроса атомарно выдаёт
один ключ. При повторе с тем же UUID и устройством-инициатором возвращается тот
же снимок bundle, даже если signed prekey уже сменился; чужое устройство или
другая цель не могут перехватить эту запись. Тесты включают параллельные запросы,
исчерпание ключей, конфликт публикации, ротацию и отзыв устройства. Подпись и
поля валидируются по формату, но **сервер не проверяет криптографическую подпись**.
Клиент должен проверить её и сверенный identity key независимо от сервера.

API не используется клиентом и не готов к production. Включать его для реальных
устройств нельзя. Его можно включить только для изолированного теста установкой
`ENABLE_EXPERIMENTAL_PREKEYS=true` на сервере. Учётная запись с доступом может
исчерпать чужие prekey; rate limit по IP не является достаточной защитой от
злоупотребления. Устройства не могут сами узнать число оставшихся ключей кроме
ответа на публикацию, нет автоматического пополнения и срока действия. Выданные
ключи и привязки request ID сохраняются навсегда, чтобы предотвратить повторное
использование: лимит 10000 записей на устройство рано или поздно исчерпается, GC
и безопасная политика истечения пока отсутствуют. Есть лимит 200 невыданных
ключей. Нет контроля сетевого downgrade, полноценного протокола аутентификации
устройств, защиты от злонамеренного сервера или миграции. SQLite сериализует
запись; проверка здесь была только на одном локальном сервере с временной БД,
не на авариях нескольких серверных процессов. Создание таблиц использует
существующий `init_models`/`create_all`; никакая миграция production-БД не
проверена, изменения схемы сначала требуют отдельного плана и резервной копии.
