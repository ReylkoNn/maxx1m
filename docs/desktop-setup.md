# Подготовка desktop-клиента

`max1m_desktop/requirements.txt` перечисляет прямые зависимости клиента и версии,
использованные в текущих модульных и локальных WebRTC-проверках. Это не
полностью зафиксированная или независимо проверенная сборка: транзитивные
зависимости и пакеты для разных ОС отдельно не проверены.

Для Python 3.11 создайте отдельное виртуальное окружение и установите зависимости:

```sh
cd max1m_desktop
python -m venv .venv
# Linux/macOS: source .venv/bin/activate
# Windows PowerShell: .venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python run_desktop.py
```

На Linux для сборки PyAudio могут понадобиться компилятор, заголовки Python и
PortAudio (`portaudio19-dev` в Debian-подобных системах). Для Qt нужны системные
библиотеки OpenGL и платформенного плагина; в тестовой среде не было `libGL.so.1`.
Для keyring нужен работающий системный backend и сохранённый исходный ключ
профиля. Не заменяйте ключ при наличии существующей зашифрованной истории или
очереди: восстановите исходный keyring вместе с резервной копией профиля.

Обычные тесты используют `requirements-test.txt`, включая подмену аудио/WebRTC.
Необязательный набор `requirements-webrtc-test.txt` дополнительно устанавливает
aiortc, av и numpy и запускает локальный тест двух peer-соединений с искусственной
тишиной. Он не использует PyAudio, микрофон, GUI, TURN или туннель. Установка
полного desktop-приложения и реальная работа аудио на целевых ОС в этой среде не
проверялись. Перед использованием приложения с чувствительными данными см.
[WORK_ITEMS.md](WORK_ITEMS.md) и [DELIVERY_LIMITS.md](DELIVERY_LIMITS.md).

## Ключи, повтор и обновление сервера

Приватный ключ устройства хранится в keyring под именем пользователя. Новый
клиент не заменяет уже существующий ключ при регистрации или добавлении
устройства. Он также не создаёт новый ключ, если для имени уже обнаружен локальный
профиль или сохранённая запись устройства: сначала восстановите соответствующие
профиль и keyring. Имя локального профиля ограничено латинскими буквами,
цифрами и подчёркиванием. Два разных сервера с одинаковым именем пользователя
пока нельзя безопасно использовать как независимые профили в одном системном
аккаунте ОС; автоматическая смена сервера для текущего устройства запрещена.

При новой регистрации/добавлении устройства записывается не содержащий приватного
ключа или пароля `pending_identity.json`, затем ключ сохраняется в keyring и лишь
после этого отправляется запрос. Повтор того же действия на тот же сервер
использует тот же ключ, если маркер и keyring совпадают. Нельзя автоматически
использовать этот маркер для другого сервера или другого действия. Ошибка записи
или пропавший/несовпадающий ключ блокируют операцию, не удаляя данные.

Если ответ сервера потерян после принятия регистрации или создания устройства,
повтор может получить ошибку «уже существует»: эти серверные операции пока **не
идемпотентны**. Ключ и маркер сохранены, но автоматического восстановления ID
устройства нет; требуется администратор и проверка по резервной копии. Не удаляйте
маркер и не заменяйте keyring, не установив состояние сервера. После успешного
ответа клиент атомарно заменяет локальное состояние и удаляет маркер; сбои
`fsync` каталога и отказ питания отдельно не тестировались. Keyring и файлы нельзя
считать единой атомарной транзакцией; одновременный запуск нескольких экземпляров
с одним профилем не поддерживается.

Новый сервер добавляет `device_public_key` к ответу `/auth/login`. Новый клиент
проверяет его, свой keyring и ID ранее зарегистрированного устройства до
сохранения авторизации. **Обновите сервер раньше клиента**: старый сервер без
этого поля не позволит войти. Это сверка с ответом сервера, а не доказательство
доверия злонамеренному серверу. Запросы авторизации больше не следуют HTTP
редиректам, чтобы не пересылать пароль или инвайт на другой адрес; в настройках
нужен конечный URL без редиректа. Используйте HTTPS или доверенный защищённый
туннель: обычный HTTP сам по себе не защищает пароль и токен в сети. Настройка и
сквозное испытание конкретного туннеля не проводились.

При обычном запуске `run_desktop.py` второй обновлённый экземпляр с той же
директорией `.max1m` не запустится: Qt-блокировка снижает риск одновременной
перезаписи истории, очереди и локальных ключей. Проверены конкурирующие процессы
и восстановление после аварийного завершения в Linux. Не запускайте одновременно
старые версии и скрипты, которые работают напрямую с файлами, не удаляйте файл
блокировки работающего клиента; сетевые файловые системы и Windows/macOS здесь не
проверены. Если папка хранилища недоступна, запуск также будет остановлен.

### PySide6 version note

The desktop and its test environment pin PySide6 6.11.3. In this Linux/CPython
3.11 sandbox, 6.12.0 reproducibly decremented `None` reference counts on Qt
void-returning methods (including `QLockFile.setStaleLockTime`/`unlock`),
leading to interpreter aborts after repeated calls. A subprocess regression
test checks this narrow case. The 6.11.3 pin passed here; it is not a claim of
full GUI or Windows/macOS certification.
